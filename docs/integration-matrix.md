# Integration matrix

Checked **2026-09-30** against the upstream sources linked below. Version observations are discovery results, **not a validated compatibility lock**. Moving branch versions and published package versions are distinguished deliberately. Documentation inspection does not establish that an integration works.

The initial host inspection reported Ubuntu 26.04, Python 3.14, Node 22, and ngspice; xschem, Magic, Netgen, and a configured PDK were absent. Actual local execution evidence belongs in the validation report and run records. EDA command adapters and non-streaming **OpenAI-compatible Chat Completions and native Ollama tool agents are implemented**, together with structured Codex/Claude CLI adapters. Local HTTP and subprocess fixture tests exercise the transports; no live external provider authentication, paid inference, or live Ollama service was validated. Responses/Anthropic adapters, interactive CLI terminals, and RL framework integrations remain **planned**. Native editor launch interfaces exist but GUI coordination and the complete SKY130 flow remain unvalidated. The tables distinguish these implementation facts from upstream capabilities and future integration proposals.

## Native GUI coordination

| Approach | X11 | Wayland / Xwayland | Decision and validation |
|---|---|---|---|
| Coordinated external windows | Native X11 editor windows; process handles and project files provide coordination. | Existing X11 tools can run through Xwayland when the compositor provides it. Window activation remains desktop-dependent. | **MVP default.** Launch with explicit cwd/configuration; track lifetime and dirty files; associate runs with immutable snapshots. Test file dialogs, focus, clipboard, scaling, reopen, and crash recovery on the chosen desktop. |
| Desktop integration | Launcher entries, file associations, and task switching improve navigation. | Similar user-facing integration, with compositor-specific activation behavior. | Follow external-window validation. Process tracking does not prove an editor is ready or a save has completed. |
| Foreign-window embedding | Qt exposes foreign-window/container facilities, but support depends on the platform and foreign application. | Xwayland does not make an X11 window a native Wayland child. Treat cross-process embedding as unsupported until demonstrated on the target compositor. | Separate experiment. Qt documents focus, stacking, rendering, and performance limitations. A web UI/Electron/Tauri shell also requires native integration to host another application's window; an HTML component is not sufficient. |

The external-window recommendation is an engineering inference from [Wayland's X11 compatibility architecture](https://wayland.freedesktop.org/docs/html/ch05.html) and [Qt's window-container limitations](https://doc.qt.io/qt-6/qwidget.html#createWindowContainer), not a completed GUI experiment. Headless batch execution remains useful even when no display server is available.

## Model APIs and external agent CLIs

Every provider configuration needs an explicit protocol, base URL, model, secret reference, supported generation options, timeout, retry/concurrency limits, and capability results. Model discovery must have a manual-entry fallback. Export configuration without secrets. A model/API key is not required for manual EDA.

Agent Lightning's current installation guide couples `verl==0.8.0` to `vllm==0.20.2` and CUDA 13.0 as its recommended path, with another documented 0.7.1/CUDA 12.9 path. These are upstream recommendations, not our validated lock. Its async collector retains incomplete rollout groups and pauses/drains inference around updates, which is relevant to variable-duration simulations. [Installation](https://microsoft.github.io/agent-lightning/stable/00-installation/), [async training](https://microsoft.github.io/agent-lightning/stable/35-asynchronous-training/)

Use a separate pinned Python 3.12 environment or container for each training backend. The host's Python 3.14 cannot satisfy current AReaL/AgentFly requirements. Do not add these stacks to the manual workspace's default installation.

The shared environment contract is `reset → observation → bounded action → real task record → independent reward → termination`. Each episode needs an isolated directory, immutable evaluator/specification, seed, tool/PDK identity, metrics, hard constraints, failure category, costs, and artifact references. Training adapters additionally preserve exact token IDs, masks, model/policy version, sampling parameters, and log probabilities when required. Human-readable chat transcripts alone are not a training dataset.

Keep three result types distinct: **circuit parameter optimization** changes design variables; **workflow/prompt optimization** changes agent behavior without necessarily changing weights; **model RL** produces updated trainable-model checkpoints. Authenticated CLIs and ordinary inference APIs are evaluation/execution backends unless connected to an explicitly supported training service. With no suitable accelerator, retain CPU simulation, baselines, trajectory collection, replay, and held-out evaluation; report weight training as unavailable.

The first RL gate is a bounded current-mirror or simple-amplifier environment, first validated against random search. Then run a small trainable-model job, save checkpoints, and compare pre/post-training held-out results under equal EDA budgets. Framework installation, populated settings, or a reward graph alone do not pass this gate.
